# 架构与取舍

这份文档记录**为什么是这样**，不记录**是什么**（那在头文件里）。

---

## 1. 一个二进制 + 课注册表，不是几十个可执行文件

上游 mini-wayland 的 `demos/` 是一个目录一个可执行文件。那边合适，
因为每个 demo 的启动方式都不一样（有的要 root，有的要 fork 子进程，
有的要指定两个设备节点）。

这边不一样：几十节课的启动方式**完全相同** —— 开一块屏幕、
每帧调一次 render。如果每节课一个 `main()`，那就是几十份
参数解析、信号处理、开显示、帧循环、落盘、统计的副本。

这不只是重复的问题。**几十份略有差异的样板，差异会被一路复制下去**，
而且越往后越难收敛 —— AI 起手会模仿它看到的上一个例子。

所以：harness 是唯一的 `main()`，课只提供一个函数。
加一节课 = 加一个目录一个 `.cpp`，不用改 Makefile，
不用注册到任何列表。

### 代价：静态初始化注册的那个坑

`MR_LESSON` 靠静态初始化把课登记进注册表。而静态初始化**只有当那个
TU 被链接进来时才会发生**。

如果把 lesson 打包成 `.a` 再链接，链接器不会拉一个"没有任何符号被引用"
的目标文件进来 —— **课会静默消失**，`list` 里少几行，没有任何报错。

解法有两个：`--whole-archive`，或者干脆不打包。这里选后者：
Makefile 里 lesson 对象是单独一组，直接链进可执行文件。
`--whole-archive` 也能work，但它把一个"你必须知道的事实"藏进了一个
链接器选项里，而这个事实早晚会有人（或 AI）在别处踩到。

## 2. `mr::Surface`：唯一的接缝

课拿到的是 `mr::Surface`，不是 `mw::display::Frame`。
中间隔的这一层只有一个函数：

```c++
mr::Surface surface_from(const mw::display::Frame& frame) noexcept;
```

换来三件事：

1. **算法能脱离显示库单测。** 验证 Bresenham 画出的像素集合，
   只需要一块 `std::vector<uint8_t>`，不需要开屏幕。
2. **上游改了 `Frame` 只改一个函数。** mini-wayland 的 `mw/render`
   与 `mw/drm` 明确标了"会变"，Step 6 还会给 buffer 加 fence 字段。
3. **`stride` 变成一个躲不开的独立字段。** 见第 4 节。

`make lint` 保证 `#include <mw/...>` 只出现在 `src/main.cpp`。

反过来说，**这一层刻意做得极薄**：不包装 `Screen`、不抽象后端、
不做 RAII 封装。多包一层只会在上游改门面时多一处要改的地方，
而 `Screen` 本来就是为库外消费者设计的门面 —— 再包一次是重复劳动。

---

## 3. render 拿到的就是要被扫描出去的那块内存

不是"课画到一块中间 buffer，harness 再拷上屏"。KMS 后端下，
`Surface::data()` 指向的就是 dumb buffer 的 mmap 地址。

中间加一层拷贝会更"安全"（不用担心双缓冲、不用担心写合并内存），
但那会把这个项目的一半意义抹掉：**看着自己算出来的整数变成屏幕上的光**。

代价是两条必须知道的事实，都写在 `mr/lesson.hpp` 与 `mr/surface.hpp` 里：

- **跨帧不保留内容。** 那是双缓冲里轮转的两块之一。需要累积的课
  自己带 `OwnedSurface`，算完 `blit()` 过来。
- **那块内存很可能是写合并甚至非缓存的。** 顺序写正常，读回慢几十倍。
  需要 read-modify-write 的算法（混合、抗锯齿、深度测试）
  应当在堆内存里算完再整块拷进来。

### Cadence 是怎么容纳这两种课的

```
Static      画一次就定了（但仍然每帧调用，见下）
Animated    用 params.time_s 做动画
Progressive 每帧往前算一点，自己在内部累积，把当前结果画出来
```

harness 的帧循环对三者是同一份代码。`Progressive` 是给路径追踪那类
课准备的 —— 屏幕上看着噪点一点点收敛，正是想看的东西。

`Static` 的课也每帧重画。开销可以忽略，换来的是
"只画了双缓冲里的一块"这类 bug 的整个可能性消失。

## 4. stride 被做成躲不开的

`Surface` 只提供 `at(x, y)` / `pixel(x, y)` / `put(x, y, c)` 三个定位入口，
不暴露"行首指针 = data + y * width * 4"这种算法。
`make lint` 禁止任何地方出现 `width() * 4`。

为什么这么较真：**offscreen 后端下 `stride == width * 4`**，
所以写错了在开发机上完全正常，上真硬件才会画面倾斜 ——
而"倾斜"看起来像几何算错了，不像内存布局问题，能瞒很久。

`OwnedSurface` 的 stride 也刻意**不做对齐**。模仿一个"差不多像硬件"
的对齐值只会让人以为自己处理好了对齐，而其实只是恰好对上了。
对齐问题必须上真硬件验，这一点不给任何虚假的安全感。

`tests/` 里有一条专门的用例：在宽 64 的内存上开一个宽 40 的 surface，
画满之后检查第 40..63 列没有被碰过。

## 5. 不变量测试，不是期望输出

把某条线的正确像素串写死在测试里，只能证明那一条线是对的 ——
而且那串期望值本身是谁算的？如果是同一份实现（或同一个 AI）算出来的，
这个测试等于自己批改自己。

不变量是从算法**定义**推出来的性质，与实现无关：
端点必被画上、相邻像素 8-连通、无重复、步数正好
`max(|dx|,|dy|)+1`、正反向画出的像素集合相同、不写出 `width()` 之外。

任何一条不成立，实现就一定错了 —— **而且不需要事先知道正确答案。**

### 实测：六种注入错误，四种是死循环

给 Bresenham 注入六种典型判别式错误：

| 注入的错误 | 表现 |
| --- | --- |
| 第二个判定用了更新过的 err | 不返回 |
| `sy` 符号写死 | 不返回 |
| 终止条件 `&&` 写成 `\|\|` | 24/94 检查失败 |
| `err` 初值写错 | 不返回 |
| `dy` 忘了取负 | 不返回 |
| `sx`/`sy` 应用位置写反 | 编译失败 |

**四种是不返回，不是画错。** 这个比例是"迭代循环必须有确切上限"
这条规则的全部理由 —— 挂死的进程比画错的画面难查得多，
它没有输出、没有退出码，在 CI 里只表现为超时。

上限取的是算法定义决定的确切步数，不是安全余量，
所以对正确实现零影响。触发即 `MR_BUG`。

## 6. `make lint`：把约定变成硬失败

上游 mini-wayland 有四个工具头文件（`parse_args` / `signal` / `env` / `color`）
躺了很久没人用。事后查出来的原因不是纪律问题 ——
**它们编译不过那边的告警集合**，谁想用谁先撞一堵 `-Werror` 的墙，
然后退回去手写 `sigaction` 和 argv 循环。人和 AI 都会做同样的选择，
而且都不会留下记录。

这件事的教训有两层：

1. **修好现成的东西。** 上游那边已经修了（4 处 `-Wshadow` /
   `-Weffc++` / 一个文件末尾缺换行），并且把 `mw/internal/`
   纳入了 `check-headers`，见其 `docs/internal-lib.md`。
2. **让"手写"这条路走不通。** 这边 `scripts/lint.sh` 用 grep 禁止课里
   出现 `main()` / `argv` / `getenv` / `sigaction` / `<mw/...>` /
   裸 ANSI 转义 / `width * 4` / 中文字符串字面量，
   并且**反向**检查 harness 确实用上了那四个工具头。

只用 POSIX sh + grep，没有依赖 —— 它必须在那块网络不稳、
装不上东西的开发板上也能跑。

七条禁令与四条正向检查都做过注入验证：逐条故意违反，逐条被抓到。

## 7. 输入为什么是终端，不是 libinput

### 开发环境是两套设备

**编码设备** —— 写代码、跑 rsync、开着 ssh 会话、编辑器、日志、git。
手放在这里。

**开发板** —— 常规嵌入式板子（CPU / DPU / GPU / BIOS / BMC），
**自带键鼠和显示器**。画面出在这块屏幕上。

循环是：编码设备上改代码 → rsync 到板子 → 切终端 tab → ssh 进去
`make` → `sudo ./bin/mini-render run ...` → **转头看板子的显示器**，
肉眼确认亮屏正常、颜色对不对。

关键在于"转头"这个动作：**只用来看，不用来操作。**

### 取舍不是可行性，是手放在哪

这一点要说清楚，因为它决定了 Step 5 该怎么做：

**`libinput` / evdev 在这个环境下完全可行。** 板子上插着真键盘真鼠标，
读得到 —— Step 5 的 `mw/input/` 正是要走那条路，而且必须走，
因为那一步的验收标准写着"鼠标移动（Cursor Plane）"，
那必须是板子上真的那只鼠标产生的 evdev 事件。板子上有，所以跑得起来。

选终端的理由是**人体工学，不是技术**：走 evdev 就得整个人挪到板子那边
去按键，而编辑器、日志、git、`make` 全在编码设备上。为了按一下空格暂停
就换一套键盘，这个循环撑不了几次。

ssh 会话本身就是一个一直在手边的键盘，而且和 `make` 在同一个 tab 里。
stdin 切 raw 模式、每帧非阻塞读一次，零依赖（termios 属于 libc）、
不需要额外权限（stdin 本来就是你的）。

附带的好处是它**不占用板子的键盘** —— 那套键鼠仍然连着板子的 VT，
可以同时用来切 VT、看 dmesg、应急登录。

### 一个会让人困惑的地方

板子上的键盘敲下去，字符进的是**板子的 tty**，不是你的 ssh 会话。
画面就在那块屏幕上，会让人下意识伸手去按那边的键盘 —— 按了没反应，
这不是 bug。

要用板子的键盘控制，就在板子的 tty 上直接跑这个程序（那时 stdin
就是那个 tty，同一套代码一样能用，不需要改任何东西）。

### 板子上那套键盘的一个真实隐患

既然板子上确实插着键盘，有件事必须写下来：

`-b kms` 跑起来之后，程序占着 DRM master，屏幕上显示的是我们渲染的画面。
**但板子的 VT 还活着，那个键盘仍然连在上面。** 此时在板子键盘上敲的
任何东西都进了那个 VT 的登录 shell —— 而屏幕正被我们占用，
所以**看不到自己在敲什么，也看不到回显**。敲到一个回车就执行了。

在一台 root 登录的开发板上，这是个实打实的隐患，不是理论问题。

正经的解法是 VT / session 管理：拿到 DRM master 时把控制台键盘切到
`K_OFF`（`KDSKBMODE`），并处理 VT 切换（`VT_SETMODE` + `SIGUSR1/2`）。
这些属于**mini-wayland 的 session 层**，不属于 mini-render ——
任何一个占 KMS 的程序都需要它，不只是这个。

在那之前，实用的规避办法：跑 `-b kms` 的时候别去碰板子的键盘。
真要用它，先 `chvt` 到一个没登录的 VT。

（这也是这套输入方案的又一个附带好处：它根本不诱使你去按那边的键盘。）

### 和 Step 5 的 `mw/input/` 不冲突

两者目的不同，会长期共存：

| | `mr/terminal.hpp` | `mw/input/`（Step 5） |
| --- | --- | --- |
| 干什么 | 遥控一个 demo | 合成器的 seat，路由事件给客户端、驱动 cursor plane |
| 事件从哪来 | ssh 会话的 stdin | 板子上那套真键鼠的 evdev |
| 拿得到抬起/修饰键/鼠标 | 拿不到 | 拿得到 |
| 谁需要 | 现在 | Step 5 的 cursor plane 验收，非做不可 |

Step 5 落地后，harness 可以改成从 `mw/input/` 填同一个 `mr::Input`，
课一行不用改 —— 这就是把输入放在 harness 而不是课里的收益。

**什么时候该切过去**：当某节课需要真正的按住/抬起、修饰键组合或者鼠标
拾取时。终端给不了那些（见下一节），到那时正确的做法是换数据源，
而不是在终端这边想办法。

### 终端拿不到的东西

不藏着，都写在 `mr/input.hpp` 开头：没有抬起事件（所以没有
`released()`，`down()` 是近似）、按住靠自动重复模拟（有初始延迟，
会一顿一顿）、没有修饰键状态、没有鼠标。

这四条决定了它适合做什么：切模式、调参数、暂停、单步、粗粒度转视角。
不适合精细连续控制。

### 恢复终端：实测覆盖到哪一步

raw 模式没恢复的话，ssh 会话会变成没有回显、没有行编辑 ——
而那一刻你看不见自己在打什么。所以这条路径单独测过（真 pty，
不是 pipe）：

| 退出方式 | ICANON+ECHO 是否恢复 |
| --- | --- |
| 正常退出（`q`） | 是 |
| Ctrl+C（SIGINT） | 是 |
| SIGTERM | 是 |
| SIGSEGV | 是（信号处理里先恢复再转默认） |
| SIGABRT（`MR_BUG`） | 是 |
| SIGKILL | **否**（捕获不了，盲敲 `reset` 回车修回来） |

`ISIG` 和 `OPOST` 必须保留，理由写在 `mr/terminal.hpp`：
前者没了 Ctrl+C 就不产生 SIGINT（一个占着 DRM master 的程序失去
Ctrl+C 意味着只能从另一个会话 kill），后者没了每行日志会往右爬。
pty 测试里顺带核对了输出全是 CRLF、零条裸 LF。

## 8. 已知的粗糙处

按影响排序，都是有意留下的，不是遗漏。

| 位置 | 现状 | 什么时候该动 |
| --- | --- | --- |
| 没有鼠标 | 只有键盘 | 需要拾取或拖拽时。终端鼠标上报（`\e[?1000h`）能做，是另一件事 |
| 跨帧状态放在文件作用域静态变量里 | lesson 01 已经这么做了 | 第二节需要状态的课出现时，再考虑给 `Lesson` 加创建/销毁上下文 |
| `LessonParams` 只有三个字段 | 课需要参数只能写死 | 需要"同一节课跑不同配置"时，加 `--set k=v` |
| 只支持一种像素格式 | 32 位 packed，字节序写死在 `Pixel` 里 | 真的出现第二种格式时改 `surface.hpp` 一个文件 |
| `Progressive` 的收敛度没有统一表达 | 各课自己报 | 有两节以上这类课之后再抽象 |
| 没有性能计时 | 只有 mini-wayland 的帧率统计 | 做到需要比较算法开销的课时 |

最后一条通用的：**一个抽象在只有一个使用者时不要建。**
上面几条都在等第二个使用者出现。
